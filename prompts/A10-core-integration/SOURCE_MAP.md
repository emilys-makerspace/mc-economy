## Thread, ownership and publication boundaries

- [FinanceMenuSupport.Audience](../../src/main/java/ca/emilybelnavis/mcmods/economy/foundation/FinanceMenuSupport.java#L17) captures player/menu/session/revision. `live()` checks that the current login is the same player instance and the menu remains valid; `reply(...)` suppresses stale publication. `grant(...)` obtains authenticated player ownership. `offered(...)` matches action and value against current server choices.
- [ServerServices.readAccounts](../../src/main/java/ca/emilybelnavis/mcmods/economy/foundation/ServerServices.java#L487) calls `checkOwner()`, requires persistent ready storage, validates ownership/inspection authority and rechecks it inside one storage transaction. `LedgerService` entry points are called on the server thread; detached readers use the supplied `ReadView` on the existing worker.
- [Worker submission](../../src/main/java/ca/emilybelnavis/mcmods/economy/foundation/ServerServices.java#L738) uses `CompletionStage<T>`; callbacks are delivered through server-tick publication. `submit(...)` refuses publication/worker/per-actor admission overflow with `StorageException.Kind.OVERLOAD`; the per-actor bound is `max(1,min(8,capacity/2))`. Never `join` these futures on the server thread. A dashboard aggregate must remain bounded and must not introduce an executor or expose SQL callbacks.
- [Shared read](../../src/main/java/ca/emilybelnavis/mcmods/economy/foundation/ServerServices.java#L774) sharing keys must have identical authorization and result types; writes end the sharing window. Any future cache/aggregate needs owner/world/session/revision binding rather than cross-owner reuse.

## Status and original-operation recovery

`Snapshot.status` and `busy` are presentation fields, not a typed operation lifecycle. [BankingScreen.reviewed()](../../src/main/java/ca/emilybelnavis/mcmods/economy/client/BankingScreen.java#L57) recognizes English status phrases; [needsRetry()](../../src/main/java/ca/emilybelnavis/mcmods/economy/client/BankingScreen.java#L271) searches for “retry”, “needs checking” or “pending”; [containerTick()](../../src/main/java/ca/emilybelnavis/mcmods/economy/client/BankingScreen.java#L309) infers review completion from “preview”/“confirm”. The approved localization/status design must replace these dependencies with server-owned structured state and offered controls before translating status copy.

[BankingAccounts.financeSubmit/start/retry](../../src/main/java/ca/emilybelnavis/mcmods/economy/foundation/BankingAccounts.java#L916) already creates and persists original operation/request IDs and canonical fields before submission, save-verifies the player, blocks a second unresolved banking intent, and performs ordered original-outcome lookup. Some legacy non-finance retry paths can resubmit the same retained intent after absence, while specified finance/card/provider/loan/account paths require a fresh request. The approved “no automatic UI resubmission” policy must distinguish lookup from mutation and preserve original outcome semantics; do not simply rename the existing Retry button. A detached old player cannot overwrite a new login's save on completion.

Proposed structured `OperationState`, reason/translation keys, receipt reference, review identity and query-bound cursors are **new design contracts**, not existing source symbols. Exact encoding/version and lifecycle transitions belong to the finalized technical plan.
