# A1-05-03 integrated acceptance evidence

## Build, tests and release

- Java 21 `./gradlew --offline build help --task runClient --rerun-tasks` initially passed
  with 65 tests. After adding targeted acceptance cases, `JournalEngineTest` and
  `JournalMigrationTest` passed. Final `./gradlew --offline build help --task runClient`
  passed with **67 tests, zero failures, errors or skips**.
- `./gradlew --offline runClient --dry-run` and `./gradlew --offline help --task runServer`
  passed. Client and server runs register the main mod source set and load the pinned JDBC driver.
- Inspected binary and sources jars. The mod metadata pins Minecraft 1.21.1 and NeoForge
  21.1.252. Entrypoints use Java 21 class files. Jar-in-jar metadata pins SQLite JDBC 3.53.4.0,
  and its nested jar contains `org/sqlite/JDBC.class`. No compiled test fixtures, probe
  classes, JUnit classes, databases, or test sources appear in the deliverable jars.

## Fixture gates

| Gate | Evidence |
| --- | --- |
| Sequential worlds and worker bounds | `SqliteStorageTest.freshReopenAndWorldIsolation`, `JournalEngineTest.sequentialWorldsKeepSameOperationIdAndEffectsIsolated`, `ServerServicesTest`. The same operation ID commits separately in two sequential fixture worlds, and reopening the first returns its own outcome. Service session/owner disposal, worker/callback boundaries, saturation, cancellation, active stalls and failed drain are covered. |
| Upgrades and rollback | `SqliteStorageTest` proves V1→V4 and rolls an injected failing migration back with the pending chain. `JournalMigrationTest` directly proves V2→V4 and V3→V4, including the backup gate, preserved identity and history. `ProjectionRecoveryTest` rejects an unknown committed record before upgrade. |
| Atomic journal, dedup and authorization | `JournalEngineTest` and `JournalServiceTest` exercise rollback, original-ID lookup, duplicate/restart behavior, authorization, overload without effects and postcommit delivery failure/cancellation. |
| Restart, replay, restore and clock | `ProjectionRecoveryTest`, `WorldBackupTest`, `WorldBackupClockTest`, `OfflineWalTest`, and `EconomicClockTest` prove committed checkpoint replay, restart/restore, sealed WAL handling, deterministic ordering and rewind/resume. |
| Actual process interruption | `JournalProcessTest` and `RecoveryProcessTest` forcibly terminate disposable child JVMs at journal commit, projection batch and clock boundaries. The reopened fixtures verify committed outcomes or absence of partial effects. |
| Exception injection | `JournalEngineTest`, `EconomicClockTest`, and migration fixtures separately inject failures and check atomicity. These and the child-process tests establish software behavior under the exercised faults. |
| Diagnostics | `EconomyCommandsTest`, `DiagnosticsReportTest` and `OperationDiagnosticsTest` exercise permission gates, sanitized status and bounded logs. |

## Isolated runtime and maintenance

- `runServer -PeconomyRunRoot=build/a1-05-03-acceptance` launched a fresh disposable
  world. The mod and SQLite JDBC loaded, economy reached READY, and `economy diagnostics`
  reported schema 4. Console `stop` drained successfully, saved all dimensions, recorded
  the clean-world witness and exited 0.
- `backupEconomyWorld` validated the stopped world. `restoreEconomyWorld` restored it
  into a new location under `build/a1-05-03-restore/server/world`. The restored identity
  matched the source and reported journal/economic checkpoints of zero. A dedicated
  server launched from that restored fixture, reached READY, reported the same identity,
  and stopped normally with a new clean-world witness. Tests with nonempty histories
  cover record and clock restoration separately.
- `runClient -PeconomyRunRoot=build/a1-05-03-acceptance` loaded the mod, client entry point,
  SQLite driver and rendering resources. The disposable client was intentionally closed
  after loading (interrupt exit 130).
- `git diff --check`, documentation links and TOML checks passed. No player worlds were used.

The dedicated and client loads were on macOS. Consecutive Minecraft worlds in one client
JVM, hardware power-loss behavior, production simulations and the full 800-listing benchmark
remain outside this acceptance. The isolated world fixture uses the core registry. Nonempty
journal, projection and clock behavior is verified by disposable SQLite fixtures.
