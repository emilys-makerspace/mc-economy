## Value model and rounding

Use reduced exact rational **minor units per one item** internally; signed-long `Money` is the published boundary. Accept positive decimal source values with currency and reference count; decimal conversion is exact. Reject unknown registry identities/currencies, duplicate keys, nonpositive prices, excessive precision and overflow. Free water is a typed built-in input, never a missing-price fallback or generally valid zero-priced configuration entry.

Source precedence for an unmodified item: explicit server override, explicit base (built-in or registered provider), registered canonical material rule where applicable (notably oak-based sticks), supported recipe/processing derivation, unavailable. Canonical stick value is two oak planks divided by four outputs, regardless of the physical crafting origin, including bamboo. This is an explicit exception to cheapest-alternative stick recipes; it preserves the oak-based tool-handle value as species wood prices rise. An override supplies the unmodified reference principal unless it declares a supported exact-component selector. Do not apply a plain-item override as an implicit replacement for damage/enchantment/content semantics. Provider conflicts are rejected, not silently resolved by order.

Keep intermediate recipe costs exact. Derive the final exact unit value including variant modifiers, convert with **one captured effective FX publication**, then `max(1, HALF_UP(exactUnitMinor))` for any priced item. For JPY the floor is one yen; no artificial hundredth of a yen. Reference quantity totals are checked multiplication of published unit minor amount by positive quantity. This means three individually priced 1/3-cent items cost three cents under the approved minimum. Water remains free as an ingredient/content; its bottle/bucket remains priced. Do not floor raw recipe inputs or apply intermediate rounding before completing a recipe.

Return both `exactUnitMinor` (provenance/derivation, not a spendable fractional price) and `unitMoney`/`totalMoney`. Ordinary user interfaces expose published money. Exact overflow or unrepresentable totals are unavailable, not clamped. Quoted and settled amounts agree. Existing FX service fees/conversion-leg rounding are separate and retain their contracts.

## Deterministic recipe derivation

Snapshot ordinary deterministic shaped/shapeless crafting, stonecutting and cooking serializer data into detached ingredients, exact output identity/count, recipe ID and source content hash. Capture expanded item tags from the same reload. Use only reviewed standard serializer implementations and registered opt-in adapters, not a recipe-type name as evidence of determinism. `Ingredient.isSimple()` can invoke custom behavior; check `!isCustom()` and detach only trusted vanilla ItemValue/TagValue data via supported access. Recipe/item remainder methods may also call custom callbacks; use trusted explicit remainder classification. No arbitrary `assemble`/mod callback execution on ledger workers. Reject recipes with unsupported output components, returned containers/byproducts or dynamic assembly; another supported path may still value the output.

Anchored inputs terminate traversal. For each unanchored output, search supported recipes and ingredient alternatives for the least exact cost per output. Canonical tie-break: recipe registry ID, then ordered ingredient identities. Empty shaped slots cost nothing; repeated consumed slots count individually. A known supported path can produce READY even if unsupported/unknown alternatives exist, with limited coverage recorded. A budget exhaustion is LIMIT_EXCEEDED, never a partial minimum.

Exclude cycles **per dependency path**, not every node in a strongly connected component. A block/ingot family may derive a block from an anchored ingot without allowing a compression loop to discount its anchor. Memoization must include canonical ancestor-set and remaining-depth context; a result rejected under one ancestor set cannot poison a different acyclic path. Cache only a completed root result across requests. A9-01 may replace this bounded search with an equivalent proven algorithm; it must preserve cheapest-supported simple derivation semantics, context-correct caching and deterministic budget outcomes.

Standard recipe participation alone does not opt a mod item into valuation. A captured vanilla registry manifest defines vanilla identities; mod contributions opt their identities into explicit values or specified supported derivation. A vanilla output with an unpriced mod input may use another known path. No fallback to emerald principal or a guessed one-cent value for missing sources.

## Processing and brewing

For the three raw metals and listed raw meats/fish, the approved raw-to-processed ratio is 0.75. One-to-one refined/cooked derivation divides raw value by 0.75: copper 2.25→3, iron 4.50→6, gold 18→24, meat/fish use revised per-species raw amounts divided by .75. Record the difference as `PROCESSING_VALUE`; apply once for the explicit raw→processed transition. Smelting/blasting/cooking alternatives do not stack uplifts; nuggets, blocks and tools use already refined ingredient values. The approved catalog extends the user's raw-food direction to named baked-potato, dried-kelp and popped-chorus transitions using the same ratio while retaining their input anchors: .25→.333… (.33 published), .10→.133… (.13), .50→.666… (.67) CAD. These detailed food calibrations are included in the catalog price approval. No universal fee on all recipes. Fuel/time/XP remain excluded from ordinary cooking estimates except for the explicit processing value.

Brewing is a separate supported adapter. `BrewingStandBlockEntity.FUEL_USES=20`: one blaze powder supports 20 operations, each processing up to three bottles. Standard per-output step cost is `prior exact potion cost + ingredient cost / 3 + blaze powder cost / 60`. Do not divide prior per-bottle cost again. Reference prices use full-batch allocation regardless of the actual stand's partial occupancy. Water is free; bottle value is counted once. Include awkward/base transitions and strength/duration/splash/lingering paths with captured potion/effect identity. No labour/time fee or arbitrary potion-effect premium. Brewing intermediates use unrounded exact values.

`PotionBrewing.getRecipes()` does not enumerate vanilla potion/container mixes. Use a narrowly scoped pinned accessor to snapshot registered vanilla mix lists and canonical input/output identities on the server thread; do not assume the public getter is complete or execute arbitrary recipes. Include the accessor/codec version in the manifest. Dragon breath returns its ingredient bottle: explicitly record that returned bottle as provenance with **no salvage credit** in this reference-cost version. Charge the ingredient once across the three outputs, count the potion's own bottle once, and do not add the returned bottle as a second input/output value. This supported brewing remainder rule is separate from the ordinary crafting-remainder exclusion.

Inaccessible potion states without a supported survival brewing path need an explicit acquisition/variant rule rather than an invented recipe. Mod brewing behavior requires opt-in supported data/adapters. A9-01 inventories the pinned registrations; no assumption that all brewing recipes are RecipeManager JSON recipes.

## Components and containers

For supported equipment: `(unmodified unit value + distinct compatible beneficial premiums) × (1 − distinct vanilla curse count / 4) × remainingDurability / maxDurability`. Non-damageable items use durability factor 1. Curses count once each; no curse=1, one=.75, both=.50. No extra salvage floor before the published minimum. Unbreaking/Mending do not change the measured durability ratio. Enchantment levels must be within explicitly supported ranges and applicable under the adapter; unknown levels/combinations yield unavailability, not silent clamping. Stored books use ordinary book value plus stored premiums, with curse discounts and no durability discount. Stored and applied enchantments are distinct components, never double counted.

Custom names have no value premium. Preserve exact names/components on the stack and in custody identity; name-neutral valuation does not imply name-neutral offer matching or demand-cohort pooling. Other unknown semantic components require explicit support. Purely cosmetic vanilla components may be registered as valuation-neutral only with an explicit canonical rule; no blanket stripping of component patches.

An ordinary filled container equals its individually valued empty shell plus its contents. Each contained item uses its own supported variant rules, unit rounding and count at the same captured currency/snapshot/FX. Sum contained published amounts with the shell, checked for overflow; do not apply the shell's damage/curse discounts to contents. Nesting is recursive and bounded. A potion or filled bucket's typed adapter contributes the entire shell+content total exactly once; do not layer generic container accounting on top of it. Filled-container valuation does not enable returned-container recipes.

Register vanilla `CONTAINER`, bundle, potion, fluid bucket and entity-bucket semantics explicitly after pinned-source review. Milk/lava/entity contents use acquisition-based content entries, water content is free; a living entity is not inferred from an arbitrary NBT string. Content unknown/unsupported anywhere means whole value unavailable; no partial total. No entity spawning, block opening, loot-table rolling or client-world queries to discover value.

## Immutable snapshots, reload and storage

One active valuation manifest per world binds algorithm/schema version, built-in vanilla identity inventory, configuration/override entries, provider IDs/revisions/data hashes, detached recipes/tags/adapter versions, processing/enchantment/content tables and canonicalization version. Content hashes include quantities/components and expanded tags, not recipe IDs alone. Snapshot UUID and revision are immutable; captured FX UUID is separate so normal FX publication need not rebuild the recipe graph.

Prepare/validate on the existing server reload lifecycle with a bounded worker; snapshot required registry data on its authorized thread. Publish only after the existing storage/journal path durably accepts the manifest and active pointer. Invalid config/provider/reload leaves the prior snapshot active and records readiness; a new game recipe reload cannot pretend stale valuation content matches current recipes. Trader quote preparation requires the active valuation and current captured recipe epoch to agree; otherwise disable affected listing until ready. Restart compares current registry/recipe/config/provider manifests before serving fresh valuations. No second financial database, scheduler or arbitrary worker callbacks.

Persist each accepted immutable manifest and original operation outcomes. Initial version retains all published manifests on disk; no automatic history deletion. Bound aggregate retained manifest data to 256 MiB, individual detached manifests to 32 MiB and reject a publication exceeding quota with explicit operator readiness. Retain active plus at most 16 compiled historical snapshots in memory (LRU); eviction is not history deletion. Historical API lookup loads a retained manifest asynchronously under the same queue/bounds. A committed consumer retains its exact result, identities and selected explanation as well as manifest IDs; a hash alone is not replay data. Never reevaluate an old receipt with new recipes or FX. Explicit future retention maintenance is outside this package.

## API/SPI contract

Expose a versioned server `ItemValuationIntegration` through the existing current-session service boundary. Public shapes (names finalized in A9-01):

- `Identity(itemId, canonicalComponents, adapterVersion)`; immutable detached canonical data, not live mutable `ItemStack`.
- `Request(identity, quantity, currency, snapshotSelector)` where selector is CURRENT or an explicit retained snapshot UUID. Current captures at admission; historical requests specify a retained FX publication or the saved result's publication. No fake past timestamp applied to current data.
- `Result(status, reasonCode, coverage, identity, quantity, exactUnitMinor, unitMoney, totalMoney, capturedAt, effectiveFrom, valuationSnapshot, configRevision, recipeRevision, providerManifest, fxPublication?, explanationRoot, explanationTruncated)`.
- `currentCached(grant, request)` is a cheap immutable readiness/cached read; `evaluate(grant, request)` is bounded asynchronous work; `history(grant, exclusiveCursor, limit)` pages at most 16 snapshot metadata records. Reads never observe/advance financial time or grant spending rights.

Authenticate grants with the current `ServerServices` session, reusing established API conventions. Cached misses return NOT_READY/PENDING; do not do unbounded inline derivation on the game thread. Availability codes include READY, UNPRICED_OPERATOR, MOD_UNREGISTERED, MISSING_INPUT, UNSUPPORTED_IDENTITY/RECIPE, CYCLE, LIMIT_EXCEEDED, OVERFLOW, FX_UNAVAILABLE, SNAPSHOT_UNAVAILABLE and NOT_READY. Internal detail remains available through operator/API diagnostics; ordinary disabled trader listings display no error explanation.

SPI data registration is lifecycle-bound and typed: provider ID, immutable revision, explicitly owned/claimed item IDs, positive base entries, supported exact selectors, optional derivation participation and registered trusted adapter version. Validate registry ownership and conflicts before atomic publication. Explicit server overrides win; two providers claiming the same source identity reject the new publication even if loader order differs. Removal creates a new manifest and invalidates affected new quotes. No late mutable callback can change a captured result. Specific mod integration implementations remain separate work.

## Trader source and price transition

Add versioned source-neutral quote/fact codecs for both account and cash preparations. Keep all old EmeraldV1 codecs/validators/implementation fingerprints available; never decode a v1 payload as an A9 source. Registry entry binds world, market/item applicability, source UUID/revision, epoch, valuation manifest, adapter/rounding/pricing versions and activation identity. Activation is an authenticated, explicit prospective journal operation after coverage/readiness, not a startup side effect or silently rerun config publication.

After an operator has explicitly activated A9 for a scope, valid configuration/recipe/provider reloads may atomically advance that already-active scope's valuation-manifest pointer and source revision/epoch in the **same durable publication**. This prospective update is governed by the installed activation policy; it does not enable a previously inactive scope. It invalidates old uncommitted quotes and preserves demand/stock/history, with no new carry. If active-source publication cannot commit with the candidate manifest, publish neither and disable admission against a mismatched game recipe epoch. Reload never silently falls back to EmeraldV1. Separate explicit activation is required only for the initial scope/implementation selection or a deliberately changed activation policy.

BOOK captures active source epoch, valuation/recipe/provider identities, exact selected goods/components/secondary ratios, stock/reputation/comparison witness and effective FX. Before a new SETTLE consumes anything, resolve the original operation first; a committed original returns its captured outcome regardless of current source, expiry or present admission. Otherwise atomically compare captured active identities against the current authoritative registry in the same financial preparation. Epoch/source/config/recipe/provider changes invalidate old uncommitted quotes before money, stock, items or delivery are consumed. Current FX freshness follows the existing quote's effective FX contract; each new quote captures an available publication. Do not change epoch on every cached read.

Preserve market assignment, currency, stock/restock, progression and demand anchors. New source/valuation revisions change original principal prospectively without revaluing prior activity or fixed loans. Journal the retirement boundary for old carry; residual records stay in old epochs, no reuse or monetary payout. New A9 pricing facts have no accumulating carry field. Preserve historical receipts, custody lots, window/model/prime/FX history under their original source versions.

The reference source uses the published reference **unitMoney** for exact merchandise in market currency times pinned standard quantity, not its old emerald count or unrounded reference internal value. Original emerald costs remain historical provenance. Construct neutral ask from that new reference principal. For a complete original two-sided equivalent cohort, capture its quantity-normalized lowest ask A and highest bid B and store the dimensionless spread factor r=min(0.8,B/A); neutral bid is new reference principal × r. A one-sided cohort uses r=0.8 for its hypothetical comparison and creates no extra listing. This retains a proven wider original gap without using emerald quantities as the new monetary principal. Bind ratio inputs/completeness and original catalog revision in the immutable witness. Secondary inputs must remain exactly captured and comparable; unsupported predicates disable the listing rather than being ignored or widening admission.

Preserve `Pricing.integral` demand/recovery and bounded reputation calculations in a **new** implementation version. Calculate the exact total for an execution quantity, divide by goods count to obtain its effective unit ask/bid, HALF_UP-round that adjusted unit to the registered minor unit with minimum 1, then multiply by goods count. Publish that unit and total together. This retains progressive demand behavior while making each quoted item unit nonfractional and eliminating carry. The effective unit may vary by selected quantity because demand is progressive; quotation captures quantity. Reference API totals remain simple published-unit multiplication.

After rounding, prove the complete equivalent-cohort maximum reachable bid is still at most 80% of its minimum reachable ask, respecting the existing reputation witness and quantity basis. If rounding/minimum destroys that proof, disable that quote: do not change HALF_UP, discard the minimum, create a free trade or widen spread silently. For example, a one-cent ask and one-cent bid cannot form a valid 20% gap. This is a deliberate availability limit on very cheap existing two-sided offers, distinct from missing catalog values. One-sided hypothetical comparisons create no actual buyback offer.

Foreign payment FX, custody/capacity, payment permission, stock/progression and actual issuance/retirement observations remain existing services' responsibility. New activity captures the actual rounded committed principal, never retroactive reference revaluation. Component-aware valuations require new exact matching/revalidation where selected; they do not automatically bypass `TradeCatalog` restrictions.
