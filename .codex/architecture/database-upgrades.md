# Administrator-approved database upgrades

## Admission and execution

`DatabaseUpgradeCommands` registers `/economy upgrade review` and `/economy upgrade confirm <token>`. Both require the directly connected permission-level 2 player, including permission on the original player and exact current player instance. Console/RCON/command blocks and `/execute as` do not supply that identity. Economy must be UNAVAILABLE, so its sole storage connection is no longer owned before maintenance can acquire `owner.lock`; an unavailable service that still owns storage causes lock refusal.

Reviews bind the normalized absolute world path, recognized source format, database/WAL/identity fingerprint and current `SchemaMigrations.CURRENT` target. They display source/target, account count, currency totals and archive limits. At most eight sessions use a bounded single maintenance executor. A review expires after two minutes and belongs to one player login/services instance. Tick observation permanently revokes its detached lease on disconnect, demotion, replacement, state change or expiry. The worker rechecks that lease immediately before durable approval publication; physical observations are tick-granular. Saved approvals retain admin UUID and UTC time, and remain bound to the exact source/target after logout so the server can stop normally.

Production `FoundationRuntime` always selects `SqliteStorage.serverStorage`; pending supported older schemas refuse with UPGRADE_REQUIRED even if a backup receipt exists. Fresh initialization and current schema startup need no conversion approval. Direct `SqliteStorage` construction remains a trusted offline maintenance/test API, not a remotely available bypass.

Run `./gradlew upgradeEconomyDatabase -PeconomyWorld=/absolute/stopped/world` after confirmation and a normal server stop. The utility requires the matching saved approval, acquires Minecraft/session and Economy ownership locks, creates a full stopped-world backup using the existing checksum/inventory protocol, then stages conversion outside the world. It never converts a running server or resets Minecraft files. A changed source, path or target needs a new review. Unknown formats, future schemas and unsupported legacy account layouts refuse without source replacement. Future registered migrations automatically target CURRENT; arbitrary unrecognized schemas are not promised support.

## Recognized legacy format and imported meaning

`LegacyDatabase` recognizes the original application_id=0/user_version=0 minor-unit schema by its complete known table/column layout, SQLite integrity/FKs and supported metadata. Optional historical currency/display tables and known trailing currency/transaction columns are allowed. Unknown tables/columns, views, triggers, generated columns, invalid UUIDs/currencies, noninteger/negative balances, conflicting primary/trading identities and incompatible current bank-account limits refuse. Accounts are bounded to 100000.

Every source table is renamed `legacy_v0_<original>` in the staged copy, retaining values and foreign-key relationships. Insert/update/delete triggers make those archives read-only. Original data remains in the complete-world backup too. Bank/trading account UUIDs, player owners, bank currencies, primary flags and exact minor-unit balances are inserted into current tables. Trading accounts retain currency-specific balances under the modern currency-neutral trading identity. New `economy:legacy-account-import` version-1 journal facts identify the exact source and imported account; nonzero openings have balanced ACCOUNT/ISSUANCE postings. Projection rebuild and per-account reconciliation verify exact source balances. Old bank accounts are assigned the existing unassigned-provider semantics during ordinary runtime recovery.

Legacy world currency is retained via a current opening FX publication. Current standard opening FX rates apply. Old ledger/FX history, stock holdings/orders/trades and price rows remain historical archives, not fabricated modern transactions or active facilities. Old physical items receive no invented cash issuance/card authority. Review and user documentation state these limits before approval.

## Atomic installation and recovery

Supported foundation upgrades stage a copy and run the existing migration chain and compatibility checks, preserving world UUID, original journal and migration timestamps. Legacy imports create a new foundation identity in the staged copy. The final staged DB is checkpointed and reopened for schema/fact validation before installation.

A forced `database-upgrade-install.properties` intent records source fingerprint, old/new DB hashes, target identity, source sidecar hashes, approval token/admin and verified backup. Normal storage initialization refuses this marker before opening SQLite. The installer verifies the archived approval and backup, atomically replaces only the database, removes only matching old sidecars, publishes the new identity and completion record, and removes the intent last. A crash at the DB/identity boundary therefore cannot be mistaken for fresh storage. The same offline command resumes a matching prepared result; it never imports the opening balances twice. Unexpected file states fail for inspection. Backups and archived source tables are retained; no automatic restore or deletion is performed. The target release must remain the same when resuming an interrupted install.
