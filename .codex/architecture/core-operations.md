# Core operations and bounded reference workload

A10-08. [Operator runbook](../../docs/SERVER_GUIDE.md), [evidence](../verification/A10-08.md).

Production scheduling, queue capacities, SQLite ownership and the30-second shutdown drain are unchanged. New opt-in `-PoperationsProbe` registers only the release-excluded inventoryProbe source set on runServer, pins its fixture heap to2–4GiB and requires a dedicated server whose world is inside a fresh `/private/tmp/economy-a10-08-*` root. It never accepts a EULA, opens a player world or installs compatibility modules. The caller supplies an existing permitted server setup. Normal artifacts and CircleCI do not enable the workload.

OperationsActors uses20 fixed synthetic player/session contexts with EmbeddedChannels and real owner grants. These are service actors, not authenticated network clients. Primary/secondary bank admission is a detached scoped fixture proof with a live actor/session predicate; physical kiosks and trader delivery are not claimed. Finite initial CAD funding and account/catalog/market/stock creation use existing journal-backed services. Money, quotes, bank transfers, FX exchanges, trader receipts and protected output custody use production paths. No raw projection seeding or financial clock acceleration occurs.

After readiness and a10-second idle baseline, the deterministic workload warms for120seconds, samples300seconds and stops submissions for60seconds. Each actor acts once per10seconds, staggered0.5seconds, for2 top-level actions/s. Each100 actions comprise40 dashboard/indexed owner-history reads,20 payment/FX reviews,20 confirmed transfers,10 trader review/confirm purchases and10 FX review/confirm exchanges. At sample second180 the normal20-request round becomes one simultaneous burst; staggering resumes after that round. Accepted action futures and confirmation-to-outcome durations are recorded separately, with underlying service-call counters. There are no replacement spends or automatic retries of uncertain operations.

Each tick records actual storage/calculation/publication queue capacity/depth and oldest queued/active ages, plus workload in-flight count and economic work state. The existing metrics expose active age rather than active worker count. The Minecraft native tick ring excludes Post event work, including Economy's callback publication. Therefore the reference tick budget uses highest-priority Pre through lowest-priority Post elapsed duration, including Economy, world work and fixture instrumentation; the native ring is reported separately. Event dispatch before/after the measured listeners and deliberate tick sleep are outside that interval.

Targets remain prospective: tick p95≤50ms/p99≤100ms; owner reads p95≤500ms/p99≤1s; confirmation→financial outcome p95≤1s/p99≤2s; burst returns to the preceding10-second queue/in-flight range within5seconds; idle drain within10seconds; normal shutdown within30seconds. A failed action, lost callback, unresolved operation or unexplained balance/custody/stock difference fails the fixture. Queue limits are never enlarged. Final reconciliation checks exact expected CAD/USD balances, immutable posting sums, zero account reservations, original receipts, transaction uniqueness, owner isolation and once-only trader custody/stock. Protected custody is distinct from physical delivery.

Normal background scheduling stays enabled; before/after macro status is retained. An observation period without a natural20-minute boundary supplies no publication-performance claim. The reference host is not a supported minimum, and synthetic service capacity does not establish20 live clients. Existing two authenticated local-client evidence remains separately qualified; external-machine evidence remains pending/manual and excluded from CircleCI. Host inventory was stopped at the user's request; unverified storage medium/filesystem and host quiescence remain unknown.

Restore keeps the current stopped whole-world format and source-owned migrations. General backup requires a matching clean shutdown witness, full checksums/identity and financial invariants; restore validates before publishing a fresh destination. A refusal after changed storage is preserved, never bypassed. Runtime readiness of a restored copy is a separate step from offline restore; old decoders and immutable source facts remain authoritative.
