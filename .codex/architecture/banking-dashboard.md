## Owner read and navigation

`LedgerService.dashboard(grant,selected,anchor)` calls `ServerServices.readAccounts` once. The supplied transaction read view composes `BankingDashboardView`: world/capture UTC, physical bank/native currency, account balances, sampled credit/loan debt, obligations and recent selected-account movements. `BankingHome` captures the live audience and publishes only after the same player/menu/session/revision remains valid. No per-frame reads, financial-time advancement, valuation qualification, new executor or database migration.

Accounts are bounded by the existing four-open-BANK cap. Credit/loan readers fetch three facilities/contracts plus one lookahead each; obligations come from retained unmet requirements and next original loan schedule rows for that sample. Sort only that bounded sample and show at most four obligations; do not claim globally earliest deadlines or portfolio totals. Sections carry AVAILABLE/UNAVAILABLE, typed reason and `hasMore`; empty available differs from unavailable. Separate account/currency money is never summed through implicit FX.

Recent activity fetches at most five original postings through `ledger_posting_account`, descending `(sequence,position)`, displays four and reports continuation. Ownership is proved against AccountCatalog before the query. Capture transaction/operation, sequence/position, exact Money, original denomination revision and recorded audit UTC. Closed owned account history is retained. This summary does not reinterpret or reverse legacy LedgerHistory pages and does not supply the later all-account/filter/detail query.

Home offers Accounts, Payments, FX, Credit, Loans, History and Refresh only when the current Access permits them. The server checks Home choices before routing. Kiosks still have branch-only origination/closure and no cash/FX authority; ATM/teller and held issued-card restrictions are unchanged. Accounts leads to branch management for opening; no account opens merely by viewing Home. Payments groups permitted existing cash, debt/loan/credit, autopay, card and claim paths. REGISTER, ADMIN and WORLD_SETUP retain specialized entry points. Banker questions remain optional.

## Operation state and bounded wire

`BankingOperation.View` carries READY/REVIEW/PROCESSING/COMPLETED/DECLINED/EXPIRED_STALE/OUTCOME_UNCERTAIN, a reason key, up to eight typed arguments, optional original operation/request/transaction receipt, review identity and expiry. Argument types are exact minor-unit MONEY, CURRENCY, INTEGER, UTC_INSTANT, UUID ID and MESSAGE_KEY. Keys/arguments and every collection/string are bounded before publication. Dynamic result keys fall back to the translated state label when no localized reason exists; legacy human explanation remains separate.

The server derives REVIEW from finite explicitly offered confirmation controls following successful source-specific capture, never from status text. Cash deposit/register and FX now explicitly offer their confirmations as well. The UI binds review identity/revision to unchanged amount and destination; changing input requires a new review. The server retains original financial admission, current menu/revision/physical proof and service expiry checks. Expired wire review emits EXPIRED_STALE and removes its confirmation. Generic refusal paths clear old confirm controls. A backend refusal/absence never revives an old review.

Snapshot codecs are paired under registrar9. Existing32-line/32-choice/12,000-UTF-8-text-byte and action/value bounds remain; total encoded snapshot is capped at24KiB, including typed data. The encoder uses a bounded temporary buffer; decode rejects oversized input and validates collection counts before allocating. Immutable dashboard sections max4 (credit/loan max3) and bounded codecs prevent portfolio-sized payloads. Oversized review terms are refused rather than silently truncated. Later changes to an already delivered codec require another transport version.

Before actual financial submission the original player intent is still save-verified with unchanged canonical request version/fields and operation/request IDs. PROCESSING is published with that original identity; completion uses the current audience. Original committed/durably rejected outcome maps to typed completion/refusal and transaction receipt. In cash continuations the retained financial COMMIT receipt is preserved across physical custody steps; observed items/claims/quarantine remain separate facts. A receipt never authorizes another physical delivery.

Unresolved pending markers suppress new financial controls and offer only the matching original-outcome lookup. Both old UI resubmission branches are removed: cash Retry always calls ordered lookup; BankingAccounts always releases proven absence for a fresh review instead of invoking a retained submit closure. Proven absence preserves original identity in a last-absent marker, clears/saves the active pointer and emits EXPIRED_STALE. Failed lookup retains the original uncertain intent. Existing backend replay, cash reserve/save/commit continuations and consented autopay retries are unchanged. Cash lookup callbacks now require a live captured audience before marker mutation/publication; no old player saves over a new login.
