## Posted history and captured details

Freeze new `OwnerHistory.Query`, `Page`, `Movement` and `Detail` contracts, separate from LedgerHistory. Query: owned account or all owned accounts, optional currency, normalized UTC `[from,to)`, finite service/type filter, page size8 default/max16. Reject reversed/negative/overflow date inputs. One row is one owned posting keyed `(sequence,recordPosition)` descending, with common transaction/operation ID to group related legs. Same-owner transfers show both movements with their account/currency; never describe them as net new income. A page may split a transaction; disclose continuation and allow exact detail. Do not guess counterparties from balancing postings.

Initial query freezes committed journal high-water; queries and details cannot include later sequences until refresh. Opaque random cursor handles refer to server-retained world/owner/menu/session/query-generation/filter/high-water/exclusive-key, with at most16 visited boundaries and one active query per menu. Previous uses retained boundaries; exhaustion offers refresh/refinement. Never offset-scan, reinterpret old v1 cursors or client-filter a truncated legacy page.

Movement fields: original transaction/operation/account IDs, sequence/position, recorded UTC instant, exact signed Money, denomination revision, posting decoder version, service/type, internal-movement association when proven. Detail loads at most64 original transaction records after owned-posting association, decodes only registered versions and returns owner-visible captured values. Status for posted history is committed; durable rejection/pending belongs to original-operation status, not fabricated movement rows.

Authoritative provenance sources:

- Journal transaction envelope: transaction/operation, sequence, `audit_utc`, economic/correction links. Outcome: service/type, request/result versions and code; canonical request/result payloads are not exposed wholesale.
- Posting versions1–4: account, signed currency amount and denomination revision; preserve `LedgerHistory.Entry` and its ascending exclusive world/account cursor.
- FxSettlement.FACT versions1–3: captured quote/publication and original settlement terms, not current FX.
- NpcFacts/ReferenceNpcFacts receipts: exact quote/actor/account/trader/market/side/principal/FX/fee/custody association. Reference quote terms retain source/proof identity; no repricing from current valuation.
- MerchantPayments receipt and committed invoice association: only after proving original operation relation, as in PaymentDiagnostics. Credit/loan/debt details use their registered original event/receipt decoders and owner association.

Represent fee as KNOWN(exact money, including zero)/NOT_RECORDED/UNAVAILABLE, and counterparty as CAPTURED(owner-visible identity)/PRIVATE/NOT_RECORDED. Unknown families still expose proved posting/envelope fields with unavailable specialized detail. A10-02-02 enumerates installed decoder dispatch per supported family and regression-checks original associations; it must not fabricate unsupported fields. Captured FX detail follows its original ID; daily and exact-time FX pages keep distinct cursors, family and pair direction. Daily maximum100 and intraday maximum16 remain; UI lower page limits win.

## Additive history projection and startup

Existing `LedgerHistorySchema.V4_INDEX` indexes posting account prefix, sequence and position. It cannot supply all owner/date/type queries. Select an additive rebuildable history projection in A10-02-02, at the next unused migration (V53 only if still unused). Do not alter journal facts, old index/cursor meaning or existing validators.

Projection revision1 rows: world/sequence/position primary key, transaction/operation/account/owner identity, recorded epoch millis parsed from audit UTC, currency/minor amount, denomination revision, service/type, source posting version and projection decoder version. Detailed terms stay in original records. Persist bootstrap target/cursor/decoder revision/readiness separately. Index owner+descending sequence/position and owner+account+descending sequence/position, with currency/type variants for offered equality filters. Date is an additional validated predicate, not a reason to sort/read all history.

Bound sparse-filter work explicitly: fetch indexed candidate batches≤256, at most16 batches per page request, on FIFO worker turns. Stop once page+lookahead is proved or indexed range ends; if4,096 candidates cannot establish a complete result, return typed WORK_LIMIT/refine-query without advancing the published cursor or claiming no more history. Never claim LIMIT17 alone bounds examined work. Check query plans for each offered index path. A future more selective index may improve this bound without changing query meaning.

Bootstrap captures a high-water and processes≤16 transactions/turn, each≤64 records; cursor and rows commit atomically. Resume deterministically after reopen. Projection unavailable until validated through its advertised high-water. New journal commits either append rows in the same transaction or are caught up by this bounded worker frontier before publication; choose bounded catch-up to avoid changing every financial handler. A query freezing a later journal high-water waits/refuses with INDEX_CATCHING_UP until coverage reaches that target. Never bootstrap on menu open or silently publish partial historical coverage. Dashboard recent reads stay independent until this projection is ready.

Wire additive schema/index/provenance/readiness validation through SqliteStorage initialization/current-store validation and `OfflineInspector.validate`, used by complete-world backup/restore. Preserve upgrade backup requirements. Validate source identity, coverage and decoder revision in bounded resumable startup work; malformed/unsupported proof is explicit failure/unavailability, never repaired journal history. Derived rows may be rebuilt with deterministic original keys, but an incomplete index is not valid complete history. Required downstream evidence includes disposable migration/reopen, frozen paging under new commits, owner isolation, sparse-filter bound and offline validator integration; choose proportional focused checks, not a cumulative suite gate.
