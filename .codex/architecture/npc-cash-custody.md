# NPC cash and physical custody — V45

A8-04-02 adds cash composition and an opt-in server adapter to the [account NPC foundation](npc-account-settlement.md). No production interaction/menu or automatic ownership is installed. Existing journal, original-operation, cash issuance, custody and progression meanings remain intact.

## Cash composition

NpcCashTrades books immutable <=30-second cash quotes with the same captured market/catalog/price/carry/stock/tick/source/reputation boundary as the account service. It needs no bank account. The selected cash currency is explicit and input tender must use that currency; mixed-currency tender is rejected. A BUY pays captured goods plus source FX fee and returns exact representable change in that selected currency. A SELL pays the explicitly selected cash currency. Unrepresentable change/payout rejects and requires a fresh explicit alternative, never an implicit account switch or ground drop.

CashDenominations freezes the original catalogue IDs/values under a canonical hash for detached worker/offline validation. No request can introduce another denomination. WithdrawalPlanner chooses exact bounded plans; original output lot IDs derive from original operation/denomination, not delivery attempt. CashIssuance conserves marked input quantities under original world/lot identities. Unmarked originals remain separately captured operator cash and require independently saved original custody; a foreign-world mark is invalid, never unmarked.

Cash FX supplier resolves from the captured village slot-0 bank or Crownstone technical fallback for bankless/wandering markets. Quote and settlement revalidate it. NpcCashFx uses actual source/target clearing principals and named supplier CASH/INCOME plus player EXPENSE fee recognition; no finite bank capital funds the goods. NPC_CASH_FX preserves0.50% Tier1 and eligible Tier2 zero; accountless users always use Tier1, including at a Tier2-only local bank. Account FX eligibility remains unchanged. The existing48-hour daily-publication reader remains until A8-06.

For BUY CAD8 from CAD10 tender: representation ISSUE I_CAD-10/B_CAD+10, goods REDEEM B_CAD-8/I_CAD+8, change representation REDEEM B_CAD-2/I_CAD+2; input lots lose10 and original protected output lots represent2. Activity records goods8 and NPC retirement8; marked representation is neutral, while unmarked10 also records operator creation10. For SELL CAD10: goods ISSUE I_CAD-10/B_CAD+10 followed by cash representation REDEEM B_CAD-10/I_CAD+10 and protected original cash output lots10. Foreign composition inserts actual bridge-to-bridge FX and explicit source fees between these groups. Every group balances by currency; every bridge starts/ends0 with nonnegative intermediate balances.

Input cash locks belong to the exact original input custody. The narrow CashIssuance.composeRedemption API requires WITNESSED custody and exact matching active lock counts, excludes only those own quantities from competing reservations and consumes/releases them atomically. It cannot admit operator cash as a tracked lot. The owning service binds actor, exact input descriptor, original financial intent and all live admission witnesses.

## Physical adapter and independent proof

TraderInventory runs Minecraft mutations only on the server thread for the active live player. Snapshot freezes selected main-inventory slot indices/counts and exact serialized full stacks, world/actor/original ID; cashSlots preserves exact marked/unmarked distinctions. matchesRequirements verifies selected noncash goods and secondary ingredients against captured component predicates, separately from exact physical stack serialization. The eventual authenticated adapter must call these checks and supply detached trusted Admission to the worker; packets cannot declare save/capacity/source authority.

fitsCombined simulates removal of those exact originals and insertion of all goods plus cash/change as one batch across36 main slots. reserve repeats this check before any removal, requires durable RESERVED custody, marks RESERVING, removes exact selected counts and marks HELD. Existing originals never get removed twice. HELD is not save evidence. saveProof uses BankingSaves.player to save and independently read actual playerdata, plus integrated-owner level.dat, comparing inventory and NeoForge markers before producing a retained immutable proof for the worker verifier.

Expired or durably rejected originals use an explicit cancellation/return claim: the worker quarantines the uncommitted input and transfers active cash locks to the original return custody; stageInputReturn requires independently saved HELD originals. Fresh collection delivers exact selected original stack components/counts without new lots. Ambiguous inputs remain quarantined.

Financial commit consumes WITNESSED original input and atomically writes money, original cash quantities/new protected lots, market/stock, progression, semantic activity and goods/cash delivery obligations. consumeCommitted retires the held marker only after the original financial receipt resolves. Physical effects remain separate from SQLite.

beginDelivery wraps the journal handler and creates an opaque one-use FreshDelivery only when a new BEGIN_DELIVERY/COLLECT actually prepares and commits; original replay creates none. markDeliveryStart checks current capacity and original descriptor and persists STARTED with an attempt generation. deliverOnce requires the live capability plus independently saved STARTED proof, a freshly reread detached DELIVERING case with matching revision/attempt, exact pre-insertion inventory and unchanged marker. It marks APPLYING before insertion, then DELIVERED. Reusing the capability cannot insert again; restored STARTED/APPLYING/AMBIGUOUS cannot regain one. A saved no-effect UNDELIVERED marker supports the original claim/collection path; uncertainty requires quarantine and audited resolution, never speculative redelivery/compensation. Saved terminal consumed/delivered markers can be cleared through bounded cleanup APIs.

Death, unload, inventory/session/source/reputation/stock changes invalidate new admission. Existing original receipts and delivery obligations survive. The eventual controller must re-resolve original outcomes before retry, flush stock tick buffers, revalidate exact reservations and provide current capacity. No exactly-once cross-store guarantee is claimed.
