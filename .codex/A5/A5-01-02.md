# A5-01-02 · Payment diagnostics

Trusted integrations can call `LedgerService.inspectPayments` and
`inspectPaymentOperation`. Both use the existing bounded storage worker
and complete through server-thread callbacks. Callers supply the
server-authenticated actor and a live operator-authority resolver.
Invoice pages restrict ordinary actors to merchant or payer participation.
Operator authority permits world-wide inspection.

Pages contain invoice terms, hold identity/state, deadline, overdue status
and the original deterministic release operation's durable result code.
Page size is 1–63, with exclusive invoice-ID cursors and one lookahead row.
Overdue filtering reports a paginated backlog without a global count.
Sampling uses the prior package's persisted clock high-water mark and wall
time without updating either.

Audit lookup first authorizes the invoice, then verifies that the requested
operation committed an invoice fact for it. It returns operation, transaction,
sequence, actor, action, UTC audit time, stable result code and receipt
association. Rejected operations lack an invoice fact and are not disclosed
through this endpoint.

Release worker failures are sanitized codes visible only to operators.
The current-process sample is transient. Persisted expiry outcomes and overdue
holds survive restart. A missing outcome is reported explicitly and does not
prove a failed release. No schema, gameplay or scheduling changes were made.
