## Follow-up Minecraft inventory persistence verification

The earlier completion statement was premature because the original witness
fixtures used arbitrary serialized files. This follow-up supplies real
Minecraft player persistence evidence and real container/SQLite restore
evidence.

Three isolated server launches completed successfully with normal shutdown,
worker drain and complete-world clean witnesses.

- First process ran actual PlayerDataStorage.save/load on a ServerPlayer with
  a fixed fixture UUID. The saved .dat contains diamond counts, a custom name
  component and world/custody/generation markers together in NeoForgeData.
  A reconstructed ServerPlayer loaded the exact saved inventory.
- A second server process opened a separate disposable copy and loaded that
  same persisted player. Both paired snapshots matched. An older expected
  witness rejected newer delivered inventory, and a newer expected witness
  rejected older reserved inventory.
- A final server run repeated the player restart checks and ran the real
  ChestBlockEntity serializer and decoder in NeoForge's initialized runtime.
  It froze actual SQLite custody snapshots before and after delivery,
  restored all four old/new database and inventory combinations into
  separate new paths, verified exact item counts/components and markers,
  and confirmed that mismatched witnesses lead to quarantine with no
  collectible claim.
- The initial standalone JUnit container attempt failed because NeoForge's
  feature flags require its initialized mod loader. The test was moved into
  the isolated server fixture and passed there.
- The opt-in inventoryProbe source set is excluded from release jars.
  The final full build, client task help and client dry run passed.

Reproduction uses Java 21 and offline Gradle. First run
./gradlew --offline runServer -PcustodyInventoryProbe
-PeconomyRunRoot=build/<new-proof-directory>.
Copy that stopped server directory to a separate new run root and run the
same command against the copy. The fixture stops the server automatically.
Phase two must emit CUSTODY_INVENTORY_PHASE2_PASS and create
world/inventory-probe-passed.txt. Gradle rejects a missing result or a fixture
failure file.

The retained passing output is under build/a5-02-01-inventory-proof/server/world
for phase one and build/a5-02-01-inventory-restores/server/world for the combined
restart/SQLite restore run. All paths are disposable fixtures.

Scope remains precise. Player persistence uses Minecraft's actual player save
and load path across processes. Container persistence uses its actual NBT
serializer/decoder with explicit file IO inside the Minecraft server process,
rather than chunk-region IO. No physical terminal workflow or crash
interruption was exercised. Save events alone remain insufficient evidence.
