## Forced interruption matrix

CustodyProcessTest starts and forcibly terminates ten disposable child JVMs.
Each child signals its precise boundary and is bounded by parent timeouts.
All cases passed.

| Boundary | Reopened observation |
| --- | --- |
| Before reservation save | Reserved intent, no saved source witness |
| After reservation save | Reserved intent and persisted source file |
| Before financial commit | Witnessed reservation, original operation absent |
| After financial commit | Original operation committed, one transfer |
| Before physical effect | Delivery attempt persisted, no physical marker |
| After physical effect | Physical marker, no acknowledgment |
| Before acknowledgment | Physical marker, no acknowledgment |
| After acknowledgment | Acknowledgment without saved inventory proof |
| Before inventory save | Acknowledgment without saved inventory proof |
| After inventory save | Saved delivery witness and delivered state |

Recovery checks both account balances and the original operation lookup.
Once the controlled reservation is independently witnessed, retry under the
same financial operation ID returns the one original result. Repeated replay
does not settle again or create a delivery marker. Startup reconciliation
quarantines every recovered case. Unknown evidence cannot create a claim.

The physical effect and inventory files in these child JVMs are explicitly
controlled detached fixtures. No Minecraft process was forcibly killed.
The first process-test invocation exposed duplicate account-owner/currency
identities in setup. Giving each fixture bank account its own owner fixed
setup, and the entire interruption matrix passed.

## Actual Minecraft persistence

Two isolated server launches used
build/a5-02-03-custody-acceptance and a separate copied run root
build/a5-02-03-custody-restart with the opt-in inventoryProbe mod.

- Phase one saved real player inventory and created a real chest at a known
  far chunk position. Minecraft stopped normally, saved all dimensions and
  recorded a clean-world witness.
- Phase two first observed that the far chunk was unavailable. Bounded
  inspection did not load it. After explicitly loading the known chunk, the
  chest contained the persisted five emeralds, custom name and custody marker.
- Moving those items to a second known chest left the original marker present.
  The original marker therefore cannot establish that items were destroyed.
- PlayerDataStorage reloaded actual player counts, custom components and
  world/custody/generation markers across processes.
- The same server fixture restored old/new real SQLite custody snapshots with
  old/new actual ChestBlockEntity serialized inventories in four separate
  disposable paths. Paired witnesses matched. Both skew directions failed
  witness matching and quarantined without a collectible claim.
- Phase two emitted CUSTODY_CHUNK_PHASE2_PASS and
  CUSTODY_INVENTORY_PHASE2_PASS. Both server launches exited 0 with normal
  shutdown and complete-world clean witnesses.

The core moved/unavailable fixture separately verifies that unproven loss
cannot create a claim or authorize operator redelivery, while preserving the
one financial transfer. Existing claim tests establish positive eligibility
from verified undelivered evidence and full-batch capacity.
